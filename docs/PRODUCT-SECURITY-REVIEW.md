# Product feature security review

Reviewed on 2026-10-19 by Codex backend/security subagent, with integration findings from the parent and release agents. Security-sensitive: **yes**. Status: **issues fixed within the reviewed local-use scope**.

This review covers the new protocol library, task organization, result bundles, first-use tutorial, help/diagnostics/usage APIs, native progress reader, and their request handling and release integration. It supplements `SECURITY-REVIEW.md`; it does not re-certify every pre-existing research workflow or claim that a local desktop service is suitable for public multi-user hosting.

## Scope and findings

Reviewed source: `app/catalog.py`, `app/demo.py`, `app/product_api.py`, `app/result_bundle.py`, `app/progress.py`, `app/api_errors.py`; related origin, validation, body-limit and security-header changes in `app/main.py`; template revision initialization in `app/job_store.py`; output encoding in the new workspace/library/result-summary frontend modules; `scripts/generate_offline_example.py`; Windows signing and release workflow changes.

| Finding | Impact | Resolution |
| --- | --- | --- |
| A terminal task could still have a registered live process or pending action. | Export could describe files still being written. | Bundles now require a terminal state, no pending/maintenance/deletion action, and no process whose saved identity still matches. Export holds the existing job file lock. |
| Checking a pathname then opening it allowed a parent directory to be substituted by a symlink. | A result/log reader could follow a replaced parent. | Readers open each untrusted path component relative to directory descriptors, using `O_NOFOLLOW`; file handles must identify regular files. FIFO opens use `O_NONBLOCK`. |
| Native quality reports use both key/value TXT and JSON inside TXT, with uppercase PASS/FAIL. | Summaries omitted existing checks or failed to translate their status. | Both existing formats are parsed with bounded reads; invalid reports are skipped. Passing execution is still explicitly distinguished from scientific validation. |
| Removing the highest protocol revision allowed its number to be reused. | Imported/exported protocol references could become ambiguous. | A persistent revision counter survives deletion. The increment and immutable template insert share one SQLite transaction. |
| JSON can carry non-finite values, and FastAPI's default validation response can fail while echoing them. | Malformed input caused a 500 instead of a useful rejection. | Templates reject non-finite numbers. Both automatic and manual validation responses retain only type/location/message, omit raw inputs and contexts, and return 422. |
| Some older mutating routes lacked the origin protection already applied to new routes. | A foreign web page could submit a local task or settings change. | Parent integration applies the existing origin check to all mutating `/api/*` requests before body parsing or execution. Native clients without an Origin remain supported. |
| An appended GROMACS log retains the old TPR's `nsteps` when the TPR is extended. | Progress could falsely show completion or an invalid ETA. | Native command-line overrides are parsed. Appended restarts and checkpoint continuation preserve observed step/time but leave the target unknown unless the log establishes it; no forced 0%/100%. |
| Offline report inline styles were blocked by the application's CSP. | Served examples lost their layout. | Both exported ZIPs and the bundled example use a local `report.css`, without relaxing script/style policy. |

## OWASP categories checked: 10/10

| Category | Result and evidence |
| --- | --- |
| A01 Broken access control | Existing local Origin checks protect new routes, and middleware protects every mutating API. Project search and IDs remain database parameters. Help names have an explicit allowlist. Result files are bounded by task-directory descriptors. This is a single-user local application; Origin checks do not replace authentication for remote hosting. |
| A02 Cryptographic failures / sensitive data | Diagnostic export returns only selected component availability and numeric versions, platform, CPU count and GPU verification; it excludes raw probes, hostnames, personal paths, task names and research data. The public tutorial strips native comments and machine/host metadata while retaining input SHA-256 records. A user-requested research bundle intentionally includes task names, notes, parameters and provenance; it is not advertised as anonymized. No credentials or signing keys were added to source. |
| A03 Injection, including XSS | SQLite statements are parameterized, including revision lookup and metadata search. Tutorial execution uses fixed argument arrays through the existing worker, with no shell interpolation. Protocol import uses Pydantic, not code evaluation. Result HTML escapes titles, notes, quality text and parameter JSON; linked filenames are URL-encoded. Frontend text uses `textContent` or existing `escapeHtml`. Report CSP permits no scripts. |
| A04 Insecure design | Tutorial execution is one CPU thread for 1 ps, queued through the existing worker. Result export excludes raw trajectories, structures, checkpoints and logs. Candidate files are capped at 500, 16 MiB each, 64 MiB in total; scanning is capped at 10,000 entries and 16 directory levels. Quality parsing is limited to 100 candidates, 256 KiB each. Native progress reads only a bounded head/tail and caches at most 128 entries. No new remote compute or account system was introduced. |
| A05 Security misconfiguration, including XXE | Application and offline report CSP, nosniff and frame protection are preserved. Oversize request responses receive security headers. No XML parser or DTD support was added. Help is served as plain text from an allowlist. The bundled example uses local CSS/images with no network dependencies. |
| A06 Vulnerable/outdated components | `pip-audit` inspected 88 installed distributions. The first pass found three advisories in the audit tool environment's urllib3 2.7.0; the parent upgraded it to 2.8.0. The repeat audit reported zero known vulnerabilities. urllib3 is not a direct project dependency or part of the Windows runtime lock. See the audit details below. |
| A07 Identification/authentication failures | No password, token, login, or session flow was added. The deployment boundary remains a local single-user process. Foreign-origin browser mutations are rejected, while command-line local clients remain possible. Remote authenticated multi-user operation is outside this release's scope. |
| A08 Software/data integrity and deserialization | Template schemas reject unexpected fields and unsupported schema versions; machine executable paths, file references and ligand charge confirmations are removed on save. Inputs must be chosen/reconfirmed for a reused protocol. Revision changes are transactional. The tutorial is regenerated from fixed source inputs and records hashes. Windows payload allowlists and symlink rejection remain; draft releases require a matching version tag and refuse to overwrite a published release. |
| A09 Logging/monitoring failures | Task execution and existing worker logs remain authoritative. Failures now include stable recovery guidance; validation returns field reasons without echoing private data. Usage reporting states that it covers local surviving task records, excludes dry runs/tutorials from both statuses and clone counts, and sends nothing externally. No multi-user security-event monitoring is claimed. |
| A10 Server-side request forgery | New product APIs perform local database/filesystem/tool operations and do not fetch user-provided URLs. The release-only signer uses a trusted timestamp-service argument; it is not exposed through a web endpoint. |

## Validation performed

- `pytest -q tests/test_product_features.py tests/test_native_progress.py`: **24 passed**. These cover immutable version numbering after deletion, strict/non-finite input, origin rejection, metadata/search behavior, escaped HTML, style packaging, symlinked parents, FIFOs, per-file/aggregate bounds, pending actions, registered live processes, report formats, diagnostic redaction, and native/continued progress semantics.
- `pytest -q -m gromacs_integration`: **3 passed**, using real GROMACS 2025.4, one CPU thread, temporary runtime roots. Coverage includes an uploaded-TPR execution and RMSD API, real checkpoint resume, and the full first-use tutorial/worker/offline bundle path.
- `scripts/generate_offline_example.py --gmx /usr/local/gromacs/bin/gmx`: completed a real 64-atom argon run, **101 energy frames through 1 ps**. The delivered image was visually inspected for axes/units and cropping. This verifies the teaching flow, not protein force fields, ligand parameterization, equilibrium, or scientific conclusions.
- A separate real continuation experiment confirmed that an extended TPR appended to a native log retains the old `nsteps`; the conservative unknown-target behavior addresses that observed case.
- Ruff check and format check passed for the new backend modules, generator, and owned tests. Parent integration runs the complete application/browser suite; the release agent reports **233 Windows Python packaging/provisioning tests passed**.
- No live worker restart or mutation of the ongoing GPU simulation was performed by these checks.

The installed test client currently emits a Starlette deprecation notice about the `httpx` compatibility path; it does not represent a failed test or a security advisory.

## Dependency and release evidence

The parent ran `.venv/bin/pip-audit --progress-spinner off --format json`. Initial advisory IDs were `PYSEC-2026-4177`, `PYSEC-2026-4176`, and `PYSEC-2026-4175`, all resolved by urllib3 2.8.0. The subsequent report contained 88 dependencies and zero vulnerabilities. Session-local evidence: `/tmp/gromacs-product-deps.json` and `/tmp/gromacs-product-deps-fixed.json`. These reports describe the installed environment at review time and are not a permanent guarantee about future advisories.

`Sign-Installer.ps1` obtains PFX material and its password from environment variables, passes the certificate directly to SignTool without a persistent certificate-store import, and deletes the temporary PFX in `finally`. The workflow withholds signing secrets on pull requests. Successful signing requires Authenticode and timestamp verification, then computes the final EXE checksum and writes a signed/unsigned status artifact. The draft-release job alone receives `contents: write`, runs only on version tags, and will not overwrite a published release.

Actual PowerShell execution, a real publisher certificate, Windows/WSL physical acceptance and production release publication were unavailable in this Linux session. They remain explicit release-checklist items. No Windows signature or published release is claimed.
